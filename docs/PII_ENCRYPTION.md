# Selected personal-data encryption

Owner-approved initial scope: `customer_profiles.contact_no`, `customer_profiles.delivery_address`, `orders.contact_no_snapshot` and `orders.delivery_address_snapshot`. Email identifiers, names, staff phone numbers, hair concerns and the separate structured-address tables are outside this first scope. Consequently this is **partial PII protection**, not encryption of every personal-data copy. Payment-card data must never be stored.

Protection is opt-in: `PII_ENCRYPTION_ENABLED=false` until a separately approved rollout. `PII_KEYRING_FILE` points to a private JSON keyring **outside the repository and public root**. Its format is `{"active":"key-id","keys":{"key-id":"BASE64_OF_32_RANDOM_BYTES"}}`. Generate cryptographically random keys locally; never put actual keys in documentation, chat, Git or database dumps. Use a separate key from MFA. Verify effective owner/service/SYSTEM-only ACLs on Windows (including inherited permissions), or mode 0600 on Unix. Preserve a separately protected recovery copy and prove recovery before changing records.

AES-256-GCM envelopes authenticate their format/key ID, table, field and immutable row ID. Every value, including NULL and empty text, has authenticated type information. New nonces prevent deterministic ciphertext. Invalid envelopes, context swaps, missing/wrong keys and tampering fail closed. Reads return decoded values only through existing authorized model flows; authentication, ownership, CSRF and audit protections remain necessary. Encryption does not protect against an attacker who controls the application and its keyring.

## Separately approved rollout

1. Verify the exact database/server/datadir and take a fresh consistent, restore-tested backup. Preserve current source and private files. No personal migration is authorized by source tests.
2. Run `scripts/migrate_pii.php` with exact `--expect-host`, `--expect-port`, `--expect-database`, `--expect-server`, `--expect-server-id` and `--expect-datadir` guards. Dry-run is default; explicit `--apply` adds six columns only. DDL implicitly commits. Repeat execution validates definitions and plans zero additions.
3. Configure the secured keyring and enable protection in the approved environment. New profile/address/Checkout writes encrypt the selected fields within the business transaction. Legacy records remain readable during transition. No GET request performs a backfill.
4. After review, invoke `PiiStorage::backfill` in a private CLI maintenance procedure with an active Administrator actor and batches of at most 100. It locks rows, verifies round trips, clears the selected plaintext fields, and audits only counts/field names. Audit failure rolls back that batch. Repeat runs skip protected records. Existing NOT NULL fields retain empty sentinels; nullable fields become NULL. No rows are deleted.
5. Verify decrypted values in memory, unchanged unrelated columns, customer/staff order views, profile/address changes, Checkout transactions and backup/key recovery. The other structured-address copies still require a separately approved scope/cutover plan before claiming full at-rest PII confidentiality.

Do not downgrade to code that ignores encrypted records or disable protection for subsequent writes. An encrypted row cannot be saved with protection disabled. Keep additive columns/current business records on recovery; restore the correct key rather than falling back to plaintext or restoring an old database over newer activity. The envelope supports reading retained key IDs and writing a new active key; bulk key rotation needs its own reviewed maintenance plan. Never delete keys needed by retained encrypted backups.

`tests/pii_encryption.php` covers primitive validation, Unicode/null/empty/boundaries, row/field/table swaps, tampering and key transitions. `tests/pii_storage.php` refuses non-disposable targets and covers schema repeatability, application reads/writes, COD stock/order preservation, ownership, audit rollback and bounded backfill. Run integration only with a secured test keyring and exact test-target guards.


The newer multiple-address feature additionally encrypts each `customer_address_book.payload_ciphertext` with this keyring, bound to table, field and address row ID. This protection is mandatory for new address-book writes, independently of the legacy opt-in flag. `scripts/migrate_address_book.php` creates an empty table only. The original PII migration's public field inventory is deliberately unchanged so it does not try to rewrite address-book payloads. Legacy structured-address rows, names and other out-of-scope data still limit any full-encryption claim.
